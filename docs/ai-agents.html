AI Agent Development Workflow

How AI agents operate in the HisabKitab repository: lifecycle, the agent roster, orchestration, and mandatory constraints.

Overview

HisabKitab uses Claude Code as its AI development assistant, with a system of 9 specialist agents that each own a specific domain of the codebase. A central orchestrator decomposes tasks, delegates to the right agents, and verifies the results.

Key principle: Every task — regardless of size — must go through the orchestrator (/manager). The orchestrator determines the right level of effort (skip the architect for a typo fix, engage the full pipeline for a new feature).

Task Lifecycle

1. Task Ingestion

The user describes what they want. The orchestrator (/manager) receives the request.

2. Triage

The orchestrator classifies the task:

  • Trivial (typo, config tweak) — Direct fix, no architect needed
  • Single-layer (e.g., "add a new API route") — Targeted agent(s) only
  • Multi-layer (new feature touching DB + API + UI) — Full pipeline

3. Architecture (if needed)

The architect-agent produces a tech-design document in tech-design/<feature>.md with:

  • Requirements analysis
  • Design decisions with rationale
  • Data model changes (section 4.1)
  • API contract (section 4.2) — enables backend and frontend to work in parallel
  • Frontend approach (section 4.3)
  • Cross-cutting concerns (section 4.4)
  • File change manifest
  • Acceptance criteria

This document becomes the single source of truth for all downstream agents.

4. Implementation (parallelized where possible)

architect-agent
       │
       ▼
   db-agent  ──────────────────┐
       │                       │ (if independent)
       ▼                       ▼
backend-agent ◄─► frontend-agent
       │                       │
       └───────┬───────────────┘
               ▼
         spec-agent                     ← update SPEC.md
               ▼
    web-test-agent  ║  mobile-test-agent  ║  review-agent    ← always in parallel
               ▼
    web-build-deploy-agent  ║  mobile-build-deploy-agent  ← in parallel if both needed

Parallelization rules:

  • db-agent + frontend-agent can run in parallel when work is independent
  • backend-agent + frontend-agent can run in parallel when the API contract is defined by the architect
  • web-test-agent + mobile-test-agent + review-agent MUST always run in parallel after implementation
  • web-build-deploy-agent + mobile-build-deploy-agent run in parallel when both apps were modified
  • Agents serialize only when there is a true data dependency (e.g., backend needs db types)

5. Review

The review-agent (read-only) checks 19 items across:

  • Security: auth on every route, no hardcoded secrets, RLS enabled, no service_role on client, prompt injection guards
  • Conventions: Zod validation, @hisabkitab/services usage, sanitized errors, activity logging, prompt versioning, token logging
  • Code quality: no any, barrel exports updated, migration naming, no console.log
  • Architecture: tech-design compliance, no layer violations, cache invalidation, authorization checks

The review ends with a PASS or FAIL verdict. If FAIL, issues are fixed before proceeding.

6. Deployment

  • web-build-deploy-agent: Runs turbo build --filter=web, then vercel (preview) or vercel --prod (production)
  • mobile-build-deploy-agent: Runs eas build --platform android --local with appropriate Java/Android SDK env

Typical Agent Tasks — Examples

Example 1: "Add expense categories to the group page"
Orchestrator analysis: Single-layer (frontend only)
→ frontend-agent: Add category display to group page
→ spec-agent: Update SPEC.md
→ web-test-agent + review-agent: Verify and check conventions
Example 2: "Add a settlement dispute feature"
Orchestrator analysis: Multi-layer feature
→ architect-agent: Design doc with DB schema, API contract, UI wireframe
→ db-agent: Migration for dispute columns, query functions
→ backend-agent + frontend-agent: (parallel, using architect's API contract)
→ spec-agent: Update SPEC.md
→ web-test-agent + mobile-test-agent + review-agent: (parallel)
→ web-build-deploy-agent: Preview deploy
Example 3: "Fix the 500 error on /api/groups/[id]/balances"
Orchestrator analysis: Targeted bug fix
→ backend-agent: Investigate and fix the route handler
→ spec-agent: Update SPEC.md
→ web-test-agent + review-agent: (parallel)

Constraints & Guardrails

Mandatory for ALL Agents

  • Security first — requireAuth() on every API route, RLS on every table, no hardcoded secrets
  • Zod validation — Every external input (API params, AI outputs, form data) must be validated
  • Layer boundaries — Pages never call @hisabkitab/services directly; API routes never write raw Supabase queries
  • Activity logging — All state-changing operations log to the activity feed (non-blocking)
  • No any — TypeScript strict mode; any requires an explicit justification comment
  • Sanitized errors — Never expose raw DB or internal errors to the client

Architectural Principles

All agents must follow the principles in tech-design/architecture-principles.md:

  • Defense-in-depth security (middleware → API → DB → RLS)
  • Server Components by default; push 'use client' as far down as possible
  • Every client mutation must call router.refresh() to sync server state
  • Testing pyramid: E2E (Playwright) → Component (Vitest + RTL) → Unit (Vitest)

How Agents Interact with the Codebase

File Ownership

Each agent has clear boundaries. The orchestrator enforces non-overlapping ownership:

  • If a frontend change requires a new query function, the orchestrator delegates the query to db-agent and the UI to frontend-agent
  • If agents discover conflicts, they report back to the orchestrator rather than overwriting each other's work

Invoking the Pipeline

To start any task, use the /manager slash command:

/manager Add a new "recurring expenses" feature

This invokes the orchestrator, which reads its spec from .claude/agents/orchestrator.md and begins the delegation pipeline. You never need to invoke individual agents directly — the orchestrator handles all coordination.
